01 / Research context

Why autonomous navigation matters on another planet

Planetary exploration creates a challenging autonomy problem: the robot must travel between scientifically interesting locations without relying on continuous human steering. Communication delays, uneven surfaces, rocks, slopes and incomplete terrain information complicate every movement decision. A robust navigation pipeline therefore needs to interpret its surroundings, represent traversable space, choose a route and assess that route for safety.

Engineering problem

Given a start location, destination and partially known environment, determine a collision-aware route while balancing travel distance, computational effort and clearance from hazards.

Research objective

Investigate how image-based terrain understanding and classical planning algorithms can be combined to support obstacle-aware planetary rover navigation in simulation.

Why images matter

Visual information can help identify rocks, rough surfaces and potentially traversable terrain. In a planning system, those interpretations can inform a map or cost representation.

Why multiple planners?

Different algorithms make different trade-offs. Comparing graph search and sampling-based methods helps explain route quality, obstacle handling and computational behavior.

02 / End-to-end workflow

From imagery to a navigation decision

A useful way to understand the project is as a sequence of connected modules. The perception component helps interpret the environment; mapping translates that interpretation into a representation the planner can use; the planner searches for a route; and simulation provides a way to evaluate the result.

Image dataset→Preprocessing / ML→Obstacle + terrain labels→Occupancy / cost map→A* · Dijkstra · RRT→Route evaluation

Stage 1 — Image preparation

Collect image examples from GitHub-hosted resources; inspect labels, image quality, licensing and relevance; and prepare training, validation and test partitions. The exact dataset size and split used in the original project are not yet available.

Stage 2 — Visual understanding

Use an image-trained model to support obstacle recognition and safe/unsafe terrain interpretation. Classification labels alone do not necessarily establish obstacle coordinates; a navigation-ready map requires a spatial representation.

Stage 3 — Terrain representation

Represent cells or regions as free, occupied or unknown; optionally attach traversal costs to reflect risk. An occupancy grid supports graph-based search, while continuous or sampled configuration space can support RRT.

Stage 4 — Navigation and feedback

Compute a route toward a goal, check its validity against the current map and evaluate whether obstacles, clearances or changing map information require replanning.

03 / Computer vision and machine learning

Teaching a rover to interpret terrain

You confirmed training an image-based model using many images sourced from GitHub. The model supported obstacle detection and safe-versus-unsafe terrain classification. That is an important part of the project because path planning depends on the quality of the environmental representation.

Dataset considerations

  • Scene diversity: rocks, open terrain, slopes and visually ambiguous regions.
  • Consistent class definitions for safe, unsafe and unknown terrain.
  • Training/validation/test separation to reduce overly optimistic evaluation.
  • Review of licensing, duplicate images and source provenance.

Potential evaluation methods

  • Precision and recall for obstacle detection.
  • Confusion matrix for terrain categories.
  • False-safe predictions, especially hazardous for navigation.
  • Qualitative inspection of difficult scenes and failure cases.

Why perception uncertainty matters

A classifier can be wrong, and an image may not reveal hidden hazards or depth. A conservative navigation design treats uncertain regions carefully rather than automatically declaring them safe. NASA's Perseverance AutoNav uses camera-derived terrain geometry to assess hazards and candidate drive paths, providing a useful real-world comparison—not proof that your project used identical hardware or methods.

04 / Algorithm analysis

Three planners, three engineering trade-offs

AlgorithmCore principleStrengthLimitation / consideration
A*Graph search guided by accumulated path cost and a goal heuristic.Can reduce unnecessary exploration with a suitable admissible heuristic.Quality and runtime depend on map resolution, connectivity and heuristic.
DijkstraExpands states in increasing known cost without a goal heuristic.Provides a clear shortest-path baseline for nonnegative edge costs.May expand more of the map than goal-directed A*.
RRTIncrementally samples the search space and extends a tree toward unexplored regions.Useful for exploring continuous or higher-dimensional configuration spaces.Basic RRT does not guarantee a shortest route and can create jagged paths.

A* scoring

f(n) = g(n) + h(n)

g(n) is the known cost from the start; h(n) estimates the remaining cost to the goal. With appropriate assumptions, A* can return an optimal grid path.

Dijkstra baseline

d(v) ← min[d(v), d(u) + w(u,v)]

Each relaxation updates the best-known route to a neighbor. It is a useful reference when comparing goal-directed search behavior.

RRT sampling cycle

sample → nearest → steer → collision check → add

The tree expands through valid samples until a goal region is reached or a stopping criterion is met.

Fair comparison

Use identical start/goal scenarios, obstacle geometry and safety constraints. Distinguish graph discretization effects from algorithm behavior and repeat stochastic RRT trials.

  • Collision margins: rover width and turning constraints matter beyond the path of a single point.
  • Map uncertainty: missing observations should not be treated as verified free space.

Frequently asked technical questions

Why not use only the image classifier to choose a route?

A classifier predicts scene or terrain information; a planner evaluates routes under geometric and safety constraints. Connecting perception to a spatial map makes navigation decisions more interpretable and testable.

What makes A* different from Dijkstra?

A* uses a heuristic to focus the search toward the goal. Dijkstra expands by accumulated cost alone. Both can find optimal graph paths under appropriate conditions, but their explored states may differ.

Why include RRT?

RRT offers a sampling-based contrast to grid graph search, especially relevant when exploring continuous configuration spaces. Basic RRT is generally about finding feasible paths, not guaranteed shortest paths.

Is this the same system as NASA's AutoNav?

No. NASA's AutoNav is a flight-proven mission system. This portfolio describes an academic project and uses NASA publications only to provide technical context and comparable design ideas.
